# F1.3 — OpenWorld Camera/Listener Ownership Boundary

Slice: `S1.3-01`

Status: boundary implemented; production scene migration deferred to S1.3-02

## Original defect

The enabled production `OpenWorld.unity` scene contains an active, tagged `Main Camera` with both `Camera` and `AudioListener`. Independently, `OpenWorldRuntimeBuilder` created another tagged `Main Camera` with `Camera`, `AudioListener`, and `ModuleZThirdPersonCamera` after creating the player.

F1.1 owner-run characterization confirmed the consequence in Play Mode: two Main Camera objects, two active AudioListeners, and extensive repetition of Unity's multiple-listener diagnostic. OpenWorld music remained audible, but camera/listener ownership failed the baseline.

## Static architecture before

```text
OpenWorld.unity
├── authored Main Camera
│   ├── Camera (FOV 60)
│   └── AudioListener
└── OpenWorld_Runtime
    └── OpenWorldRuntimeBuilder.Start()
        ├── CreatePlayer()
        └── CreateThirdPersonCamera(player)
            └── dynamic Main Camera
                ├── Camera (FOV 50, Skybox)
                ├── AudioListener
                └── ModuleZThirdPersonCamera
```

The dynamic camera is the gameplay camera because it owns the third-person controller and targets the runtime-created player. The authored camera is transitional production-scene debt.

## Ownership decision

S1.3-01 introduces:

- `OpenWorldSceneRoot`: scene-scoped lifecycle and explicit owner of the runtime player, gameplay Camera, gameplay AudioListener, and third-person camera controller;
- `OpenWorldGameplayCameraBuilder`: stateless, explicit construction boundary for the existing dynamic gameplay-camera composition.

No separate `OpenWorldBootstrap` is introduced. The existing serialized `OpenWorldRuntimeBuilder` already serves as the broad procedural entry point, so an additional bootstrap would add ceremony without reducing responsibility in this slice.

Until S1.3-02 serializes the ownership boundary directly, `OpenWorldRuntimeBuilder` resolves `OpenWorldSceneRoot` on its own scene GameObject and adds it only when absent. `[DisallowMultipleComponent]` and the resolve-before-add path prevent duplicate roots during the current startup path.

## Architecture after S1.3-01

```text
OpenWorld_Runtime
├── OpenWorldRuntimeBuilder
└── runtime-attached OpenWorldSceneRoot
    ├── Player reference
    └── gameplay Main Camera reference
        ├── Camera (FOV 50, Skybox)
        ├── authoritative gameplay AudioListener
        └── ModuleZThirdPersonCamera (Player target)
```

`OpenWorldRuntimeBuilder` still creates the player and retains all existing HUD, theme, music, NPC/world, and procedural composition responsibilities. It no longer contains camera construction details: it delegates creation and transfers explicit references to the scene root.

## Gameplay camera behavior preserved

The extracted builder retains the existing values and order:

| Property | Preserved value |
| --- | --- |
| GameObject name | `Main Camera` |
| Tag | `MainCamera` |
| Field of view | `50` |
| Clear flags | `Skybox` |
| Components | `Camera`, `AudioListener`, `ModuleZThirdPersonCamera` |
| Target | Runtime-created player Transform |
| Initial offset | `(0, 3.2, -4.5)` transformed by target rotation |
| Look target | Player position plus `Vector3.up * 1.6` |

## AudioListener ownership

The builder creates the gameplay AudioListener on the same GameObject as the gameplay Camera. `OpenWorldSceneRoot.Initialize` validates that the Camera, AudioListener, and `ModuleZThirdPersonCamera` share an owner before entering `Ready`.

No listener manager, arbitration, global owner, `DontDestroyOnLoad`, scene-wide lookup, or cleanup/destruction behavior is introduced.

## Production behavior impact

Camera construction is a behavior-preserving extraction. The same runtime camera and components are created with the same configuration, target, position, and look direction. The only new runtime object state is the scene-scoped ownership component and its references/lifecycle status; it has no gameplay authority.

The production defect intentionally remains in S1.3-01 because the authored scene camera and listener are unchanged. S1.3-02 owns removal of that competing serialized composition.

## Transitional scene camera status

`Assets/ModuleZ/Scenes/OpenWorld.unity` is not modified in S1.3-01. Its authored active Main Camera and AudioListener remain transitional debt. Code does not destroy, disable, arbitrate, or search for that camera.
