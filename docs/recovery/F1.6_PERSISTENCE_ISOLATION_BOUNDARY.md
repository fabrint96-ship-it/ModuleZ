# F1.6 Persistence Isolation Boundary

## 1. Incident motivation

A prior local PlayMode validation allowed a nondeterministic Duel result to reach production `SaveGame()` and modify the developer profile. The post-incident profile is treated as read-only; this slice does not restore, delete, or rewrite it.

## 2. Scope

This slice changes only persistence root resolution, integrates save and settings writes with that root, and adds focused PlayMode validation. Serialization, schemas, gameplay, scenes, packages, and project settings are unchanged.

## 3. Baseline

Branch base: `develop` at `c9f27e6f7c43162832a5c6c1712e2c3063ec348d`.

## 4. Current persistence coupling

Before this slice, `ModuleZSaveManager` and `ModuleZSettingsManager` independently combined their filenames with `Application.persistentDataPath`. Runtime tests therefore could not safely exercise production writes.

## 5. New path boundary

`ModuleZPersistencePaths` is a static, non-MonoBehaviour path provider in `ModuleZ.Core.SaveSystem`. `RootPath` resolves to the explicit override when present and otherwise to `Application.persistentDataPath`.

## 6. Production default behavior

With no override, save and settings paths are unchanged:

- `Application.persistentDataPath/modulez_save.json`
- `Application.persistentDataPath/module_z_settings.json`

No environment-specific production path or automatic test detection was introduced.

## 7. Explicit override contract

The public contract is:

- `string RootPath { get; }`
- `void SetRootOverride(string path)`
- `void ClearRootOverride()`

The setter rejects blank paths and normalizes the selected root with `Path.GetFullPath`. The override field is private and can only be changed through the controlled API.

## 8. SaveManager integration

`ModuleZSaveManager.SavePath` now combines `ModuleZPersistencePaths.RootPath` with `modulez_save.json`. `SaveGame`, `LoadGame`, `DeleteSave`, `HasSave`, and `GetSaveData` therefore operate on one selected root without changing their data or behavior.

## 9. Settings integration

`ModuleZSettingsManager.SettingsPath` now combines the shared root with `module_z_settings.json`. Settings data, application, reset, and serialization semantics are unchanged.

## 10. Directory behavior

`SaveGame` and `SaveSettings` create the selected root immediately before writing. Read-only operations do not create directories.

## 11. Static-state rationale

The private `rootOverride` is the single intentionally introduced mutable static field. It is narrowly scoped, explicitly resettable, and changes file location only. `STATIC-020` initially reported it as a heuristic warning; the versioned baseline received exactly one reviewed entry explaining this approved safety seam. No other allowlist was changed.

## 12. Real-profile guard

Before validation, both real-profile files were fingerprinted by existence, size, UTC modification time, and SHA-256. The same fingerprints were verified after PlayMode, combined tests, and `all`. Both remained unchanged. The fingerprints themselves are local validation evidence; save/settings contents are not recorded here.

## 13. Isolated-root strategy

Each fixture uses a unique directory below the operating-system temporary root (`ModuleZValidation/Persistence/<guid>`), outside `Assets` and outside `Application.persistentDataPath`. The override is installed before any write and cleared during teardown. The isolated directory is deleted after each test.

## 17. Production impact

Production changes are limited to the path provider and two persistence integrations. Default paths and all serialization behavior remain equivalent. No scenes, packages, project settings, production asmdefs, Duel code, or gameplay code changed.

## 18. Known limitations

The override is process-global and must be set before any persistence-capable bootstrap or gameplay operation. Tests must always clear it in teardown/finally. This slice does not redesign persistence concurrency, atomic writes, migrations, profiles, or save schemas.
