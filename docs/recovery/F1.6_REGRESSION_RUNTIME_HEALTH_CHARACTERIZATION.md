## 13. Test pyramid

- **L0 — source/static ratchets:** fast, deterministic checks for files, scene YAML, GUIDs, Build Settings, dependency direction, forbidden calls, and creation-path counts. They cannot prove runtime behavior.
- **L1 — EditMode unit/invariant tests:** contracts, validation, mappings, and static-session state with strict setup/teardown. They do not prove scene composition.
- **L2 — PlayMode scene/runtime tests:** production-scene loading, R3 readiness, ownership counts, teardown, and focused runtime lifecycle. They should avoid save-producing result paths until persistence is isolated.
- **L3 — canonical smoke automation:** sequential Boot-to-MainMenu-to-OpenWorld-to-Duel-to-OpenWorld orchestration with timeouts, logs, and artifact output. It proves integrated paths but is slower and more fragile.
- **L4 — Project Owner manual acceptance:** visual, audio, input feel, UX, hard-to-drive outcomes, and final release judgment. It complements rather than replaces L0-L3.

## 14. L0 static validation

The first validator should be a read-only Editor/command-line entry point with deterministic nonzero exit on failure. It should validate Build Settings, exact root/bootstrap GUID composition, zero production `Duel3DDebugBootstrap`, no authored OpenWorld camera/listener, one camera/listener creation path, absence of builder-owned lifecycle `Start`, and diff-aware Foundation ratchets. Every heuristic must label itself heuristic and use a reviewed baseline/allowlist so pre-existing debt does not make every run fail.

## 15. L1 EditMode strategy (5 candidates)

1. `DuelContext` construction and value immutability surface.
2. `DuelOutcome` exact members and `DuelResult` value surface.
3. `DuelResultBridge` invalid outcome/rival, identity mismatch, missing processor, and single dispatch.
4. `ModuleZDuelSessionState` payload-before-active semantics, complete reset, and idempotent `Clear`.
5. `DuelTransitionBridge` invalid-rival rejection and one-way compatibility projection, with every static field restored in teardown.

These tests can use existing public APIs without production redesign. Tests that call bridges must snapshot/reset `ModuleZGameState`, session state, and `Time.timeScale` to prevent cross-test contamination.

## 17. L3 smoke strategy

Translate the F1.5 LIFE checklist into a state-driven harness rather than fixed sleeps: load Boot; observe Main Menu; enter OpenWorld; await R3; assert ownership; start a known Duel; await Duel R3; perform a legal invariant-level action; observe AI transition; drive one safe result path; await OpenWorld R3; repeat; validate session/owners/logs. Victory/Defeat/Rematch can remain L4 until deterministic drivers and save isolation exist. Every stage needs a bounded timeout and a diagnostic naming the last achieved state.

## 18. L4 owner validation

Owner validation remains authoritative for movement/camera feel, visible theme/HUD, audio, rival presentation, nuanced result messaging, progression correctness, hard-to-force Victory/Defeat/Rematch/Draw, and subjective regressions. Automated layers should reduce repetition, not declare those observations without exercising them.

## 19. Scene testability

All three production scenes can be loaded by PlayMode tests, and procedural roots expose R3 state suitable for `WaitUntil` assertions. OpenWorld and Duel are deterministic enough for ownership/readiness assertions. Test-only scenes are not initially required; prefer production-scene invariant tests to prevent composition drift. Boot creates persistent managers, so full-flow tests must run serially and clean application-scoped objects between cases. Directly loading OpenWorld or Duel is suitable only for focused tests whose prerequisites are explicitly seeded.

## 20. Persistence safety

`ModuleZSaveManager` reads/writes/deletes `Application.persistentDataPath/modulez_save.json`. `ModuleZSettingsManager` reads/writes `module_z_settings.json`. Boot's persistent `ModuleZSaveBootstrap` loads the real save; `ModuleZAutoSaveController` saves on pause/quit; Duel Victory/Defeat/Abandon, OpenWorld portals, and pause-menu actions also call `SaveGame`.

Therefore automated result/smoke tests are **unsafe against a developer/user profile today**. Before L3, provide a test-only temporary-storage boundary or explicit save suppression/test profile selected before Boot. Back up/restore is weaker because interruption can strand modified data. Focused L1/L2 tests must avoid save-producing paths until isolation exists. No persistence change is made in this slice.

## 21. Determinism analysis

| Source | Assessment | Strategy |

| Root initialization and ownership | Assertable at invariant level | Wait for Ready/Failed with timeout, not frame count. |

| Match timers, invokes, coroutines, delays | Controllable but slow | State waits, bounded timeouts, restore `Time.timeScale`. |

| Procedural world/board construction | Deterministic enough structurally | Assert required roots/components, not incidental ordering. |
| Save/load/static state | Environment-dependent | Temporary profile plus explicit reset. |

## 22. Static state contamination

Static mutable state includes `ModuleZGameState`, `ModuleZDuelSessionState`, singleton `Instance` accessors, achievement state, SaveBootstrap's `loaded` flag, and timing state. Domain reload configuration can determine whether these reset between runs. Fixtures must not assume a fresh process: establish and restore known GameState/session values, destroy scene-local instances, unload scenes, restore `Time.timeScale = 1`, and either force domain reload or provide explicit test reset hooks scoped to test assemblies. PlayMode suites should not run these fixtures in parallel.

## 23. Runtime isolation

Boot establishes DDOL `ModuleZGameManager`, `ModuleZSceneController`, `ModuleZUIManager`/EventSystem, SaveBootstrap, and related runtime composition. Those are legitimate application-scope objects but can contaminate later tests through duplicate guards and static `Instance` fields. Use one canonical sequential full-flow fixture per player process, or teardown every persistent root and verify static cleanup. Focused scene tests should deliberately choose whether Boot managers are present. Logs should use scoped expected-message handling so genuine errors still fail the test.

## 34. REC-007 closure criteria

REC-007 can close only when:

1. A checked-in reproducible command runs L0, L1, and the required L2 suite.
2. P0 static invariants cover build scenes, debug separation, roots, lifecycle entry, camera/listener paths, and contract/result authority.
3. L1 covers context/result validation and deterministic session lifecycle.
4. L2 proves OpenWorld and Duel R3 readiness, singular OpenWorld camera/listener ownership, ResultManager teardown, and direct-fallback isolation.
5. A persistence-safe automated normal OpenWorld-Duel-OpenWorld roundtrip runs reproducibly, or a documented manual-only blocker is explicitly accepted without misreporting it as automated.
6. Test XML and logs are produced with meaningful nonzero failure exits.
7. CI independently executes the stable mandatory subset on PRs and `develop` with pinned Unity and artifacts.
8. The L4 owner checklist remains versioned for behavior not safely automated.
9. The suite itself is run successfully from a clean checkout with no user-save mutation and no unexplained flakiness.
