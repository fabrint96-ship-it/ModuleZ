## 3. Existing scene lifecycle model

Boot serializes an application-like `ModuleZ_Runtime` root. OpenWorld serializes one `OpenWorld_Runtime` with both `OpenWorldRuntimeBuilder` and `OpenWorldSceneRoot`. Duel serializes one `DuelSceneRoot` GameObject with `DuelSceneRoot` and `DuelBootstrap`.

OpenWorld lifecycle is builder-driven: Unity invokes `OpenWorldRuntimeBuilder.Start`, the builder composes nearly the whole scene synchronously, then asks the root to record four owned references. Duel lifecycle is root-driven only through runtime-object creation: Unity invokes `DuelSceneRoot.Start`, the root asks Bootstrap to create/configure a runtime builder, marks itself Ready, and Unity later invokes that builder's `Start` to build gameplay.

There is no shared lifecycle framework, no teardown protocol, no readiness callback from either runtime builder, and no root-level ownership cleanup.

## 4. Scope/ownership taxonomy

Scopes used here:

- **APPLICATION** — intended to survive scene changes.
- **SESSION** — cross-scene Duel transport from accepted entry until result cleanup.
- **SCENE** — destroyed with the loaded scene.
- **RUNTIME CHILD** — dynamically composed, long-lived for its scene.
- **TEMPORARY BUILDER** — short-lived construction helper.

Ownership classifications:

- **EXPLICIT** — serialized or held by a direct owner reference.
- **TRANSITIONAL** — explicit enough for current recovery but retains fallback/global access.
- **IMPLICIT** — lifetime follows a host/Unity behavior without a complete owner contract.
- **AMBIGUOUS** — multiple actors can appear to own lifecycle or failure.

## 5. Readiness taxonomy

- **R0** — component exists.
- **R1** — required dependencies accepted.
- **R2** — owned runtime objects/references created.
- **R3** — runtime initialization completed.
- **R4** — gameplay operational.

Both existing SceneRoot `Ready` values currently guarantee **R2**, not R3 or R4. Successful owner runtime evidence previously reached R4, but that observation is not encoded by the state properties.

## 7. OpenWorld initialization order

`OpenWorldRuntimeBuilder.Start` determines order:

1. `GetComponent<OpenWorldSceneRoot>`; add one if missing.
2. Resolve theme data.
3. Add HUD overlay coordinator.
4. Add message, progress, achievements, stats, achievement-toast, zone, and system-message HUD components. Their `Awake` methods may build presentation immediately.
5. Add pause controller.
6. Add selected theme builder and synchronously call `Build`; it adds lighting/ground/buildings/props/roads/walls/NPC builders and objects.
7. Add music controller and start theme music.
8. Create temporary `PlayerBuilder`, construct Player, then schedule the temporary host for destruction.
9. `OpenWorldGameplayCameraBuilder.Create` constructs Main Camera, Camera, AudioListener, controller, and target binding.
10. Call `sceneRoot.Initialize(player, camera, listener, controller)`.
11. Start pending-message readiness coroutine.
12. Log OpenWorld generated.

Unity decides when the builder's `Start` runs relative to other independently enabled `Start` methods; the code imposes no Script Execution Order. `AddComponent` invokes `Awake` synchronously, but later `Start` calls on created components are Unity-scheduled.

## 8. OpenWorld readiness semantics

`OpenWorldSceneRoot.Initialize` transitions Uninitialized → Initializing, validates non-null Player/Camera and same-GameObject listener/controller ownership, stores those references, then sets Ready.

Ready guarantees:

- one accepted Player reference;
- one accepted gameplay Camera reference;
- listener and third-person controller exist on that Camera GameObject;
- those four references reached the root after builder construction calls returned.

Ready does **not** guarantee:

- HUD/pause/theme/music controllers completed their Unity `Start` lifecycle;
- message HUD is available or its pending message displayed;
- player/camera controller is operational for a frame;
- theme content is complete/correct;
- no earlier component logged an error;
- later runtime components remain healthy;
- teardown/cleanup ownership.

HUD, pause, theme, music, Player, and Camera are all created before Ready. Message-system readiness is a separate two-second polling coroutine after Ready. A second `Initialize` while Ready returns true without revalidation; calls while Initializing or Failed return false. Failed cannot recover. Initializing has no normal asynchronous wait, but an unexpected exception between the state assignment and `Fail` could leave it stuck.

## 9. OpenWorld failure propagation

The builder does not capture the bool returned by `sceneRoot.Initialize`. It always starts pending-message work and logs generated after a false return. Root validation failure leaves all previously created HUD/theme/music/player/camera objects alive. There is no cleanup or disable step.

Player/theme/camera construction exceptions are not caught. They abort `Start` through Unity, leave the root Uninitialized (or any earlier state), and leave already-created objects alive. Consequently OpenWorld can be partially composed with root Uninitialized/Failed, or can continue presentation work while root Failed.

If `OpenWorldSystemMessageHUD.Instance` remains unavailable after two seconds, the builder logs a warning, still clears pending/last messages and `ReturningFromDuel`, and refreshes rival HUD state. This is PRESENTATION_DEGRADED and can lose the visible return message without changing SceneRoot state.

## 11. Duel initialization order

1. Unity calls `DuelSceneRoot.Start`.
2. Root verifies Uninitialized and resolves the serialized/same-object Bootstrap.
3. `Initialize` sets State = Initializing.
4. Bootstrap validates owner and resolves one accepted context from active session or fallback.
5. Bootstrap creates child `Duel3D_Runtime`, adds `Duel3DRuntimeBuilder`, and immediately calls `Initialize(context)`.
6. Bootstrap returns object/builder references.
7. Root stores them and sets State = Ready.
8. Later, Unity calls `Duel3DRuntimeBuilder.Start`.
9. Builder synchronously constructs/configures arena, board, AI, match resolver, result manager, HUD, pause, feedback, visuals, and other runtime content.

Therefore the root reaches Ready before step 8.

## 12. Duel readiness semantics

Duel Ready currently means **R2**:

- a child runtime GameObject exists;
- a builder component exists;
- the builder accepted one `DuelContext`;
- root holds direct references to object and builder.

It does not mean board, HUD, AI, result manager, rules, feedback, camera/controller, or gameplay has been built. There is no runtime-builder completion/failure callback and no root transition after builder `Start`. Runtime construction can fail after the root reports Ready; the root remains Ready and cannot represent degraded/failed runtime state.

## 13. Duel failure propagation

Bootstrap reports synchronous owner/context/runtime-object/builder-acceptance failures to the root, which sets Failed. It catches exceptions during runtime GameObject/AddComponent/Initialize and destroys the runtime object. After Bootstrap returns success, failures belong to `Duel3DRuntimeBuilder.Start` and are not propagated.

If `Duel3DResultManager.Initialize` returns false, the builder logs an error and returns after arena, board, AI, match resolver, and related roots already exist. It performs no cleanup and root remains Ready. Any unhandled sub-builder/component exception similarly appears as a Unity runtime error while root remains Ready. Missing SceneController during result return logs an error only after flags/stats/progression/messages/save/session clear have occurred; navigation stops and the resolved Duel remains loaded.

## 17. Duel3DResultManager.Instance lifecycle audit

`Duel3DResultManager` has no `OnDestroy`; `Instance` is not explicitly cleared. It is scene-local because its host `Duel3D_Runtime` is not DDOL. Unity's destroyed-object null semantics usually make the old reference compare equal to null, so the next scene's `Awake` can assign a new instance. Nevertheless the managed static reference persists until overwritten, code using non-Unity reference semantics could observe residue, and there is no explicit lifecycle invariant.

The builder retains a direct result-manager reference for match completion; only `DuelPauseMenuController` uses `Instance` for abandon. This is P1 lifecycle/dependency debt for S1.5-03, not result authority and not a proven current P0 regression.

## 18. SessionState lifecycle

```text
inactive (HasActiveDuel=false)
→ DuelTransitionBridge.Begin
→ StartDuel: active=true; overwrite RivalId/IsRematch/ReturnPosition
→ DuelBootstrap reads active transport once into accepted DuelContext
→ runtime/result uses accepted context
→ SaveGame
→ ModuleZDuelSessionState.Clear
→ inactive=false; IsRematch=false; RivalId/ReturnPosition stale
```

`Clear` resets `HasActiveDuel` and `IsRematch`, but not `RivalId` or `ReturnPosition`. Normal Bootstrap reads those fields only when active; the next normal `StartDuel` overwrites all three, so stale inactive values cannot control the normal path. Lifecycle invariants are implicit: callers can mutate public static fields directly, no method enforces legal transitions, and no token ties Clear to the active Duel.

## 19. Direct-scene fallback lifecycle

Activation condition: `DuelBootstrap` sees `HasActiveDuel == false`. It constructs one accepted context from `PendingDuelRival`, `CurrentDuelIsRematch`, and `OpenWorldReturnPosition`. It does not set `HasActiveDuel` or create an artificial session. Runtime and result manager use that accepted context. Result processing still calls `Clear`, which keeps the state inactive and clears rematch. Return flags/messages/save/navigation behave normally.

The fallback is isolated from normal production because normal entry calls `StartDuel` before loading the scene. It likely supports Editor/direct-scene compatibility, remains appropriate during EP-01, and has static/compile evidence but no dedicated direct-scene runtime observation. It is TRANSITIONAL, not a normal authority.

## 20. Boot/DDOL boundary

Boot serializes `ModuleZ_Runtime` with `ModuleZGameManager`, `ModuleZSceneController`, `ModuleZUIManager`, `ModuleZAutoSaveController`, and `ModuleZSaveBootstrap`. GameManager, SceneController, UIManager, and SaveBootstrap each call `DontDestroyOnLoad` on their shared GameObject; one such call persists the whole root and all sibling components. GameManager/SceneController/UIManager perform Instance duplicate checks that destroy a duplicate root. SaveBootstrap uses static `loaded` and otherwise relies on shared-root lifetime; AutoSave has no independent guard but persists as a sibling.

UIManager creates a separate DDOL EventSystem only when none exists. No ModuleZ source reference creates `DelayedActionManager`; the owner-observed root is Unity runtime infrastructure associated with delayed actions, not a ModuleZ-owned component.

No scene-scoped OpenWorld/Duel root, builder, HUD, result manager, camera, or listener calls DDOL. F1.5 should not redesign this application boundary; ApplicationRoot belongs to EP-02. It should touch Boot only if a concrete lifecycle stabilization requires it, which current evidence does not.

## 25. REC-006 characterization

REC-006 is **CHARACTERIZED**, not closed.

Concrete findings:

- **P1:** `OpenWorldRuntimeBuilder`, not SceneRoot, initiates lifecycle and may create the root dynamically despite serialized ownership.
- **P1:** OpenWorld ignores root initialization failure and has no failure cleanup/stop path.
- **P1:** Duel SceneRoot Ready is issued before runtime initialization and cannot receive later failure.
- **P1:** Result-manager acceptance and sub-builder failures can leave partial Duel while root remains Ready.
- **P1:** scene-local result-manager/coordinator Instance cleanup and ownership are incomplete.
- **P1:** session/fallback lifecycle relies on implicit static conventions.
- **P2:** OpenWorld and Duel builders compose many unrelated gameplay/presentation domains and retain numerous builder components/objects without common ownership/teardown.
- **P2:** broad decomposition, optimization, and procedural-content redesign exceed F1.5.

Only P1 readiness/failure/lifecycle stabilization belongs in S1.5-02 through S1.5-04. There is no evidence-based P0 item.

## 28. Proposed S1.5-02 scope

**OpenWorld SceneRoot Readiness & Builder Ownership**:

- require/validate the serialized root for production while explicitly deciding fallback compatibility;
- make one owner initiate initialization rather than builder/root ambiguity;
- check and propagate `Initialize` outcome;
- stop success/message continuation on fatal root failure;
- define R3 completion only after required composition succeeds;
- preserve builder gameplay/content responsibilities and camera behavior;
- avoid broad builder decomposition.

## 29. Proposed S1.5-03 scope

**Duel Lifecycle, ResultManager Ownership & Failure Propagation**:

- delay SceneRoot Ready until runtime builder reports R3 success;
- add a narrow builder completion/failure callback/result without framework work;
- propagate result-manager/subsystem initialization failure to root;
- clarify cleanup of partially created runtime;
- make result-manager lifecycle explicit, including `Instance` reset or removal of pause-menu static access if narrowly safe;
- preserve F1.4 accepted context/result authority and gameplay.

## 30. Proposed S1.5-04 scope

**Session / Fallback Lifecycle Stabilization**:

- encode/validate active/inactive transition invariants around Start/Clear without creating new global state;
- decide safe handling of stale inactive rival/return values based on consumers;
- explicitly classify and guard direct-scene fallback as development/compatibility behavior;
- ensure fallback/result cleanup cannot contaminate a later normal session;
- preserve return markers/save compatibility and avoid full REC-008 decomposition.

## 31. Proposed S1.5-05 closure criteria

F1.5 closure should require:

1. OpenWorld and Duel roots report a documented R3 state, not merely object acceptance.
2. Fatal initialization failures reach the owning root and do not produce success continuation.
3. Partial runtime objects are cleaned up or explicitly disabled/owned.
4. Normal OpenWorld and Duel composition has one lifecycle initiator each.
5. ResultManager scene lifetime/static access is deterministic across repeated scene loads.
6. Session active/inactive and fallback invariants are explicit and statically audited.
7. Existing Boot→OpenWorld→Duel→OpenWorld, repeat, rematch, save, camera/listener, and result behavior passes owner validation.
8. Failure-focused validation covers missing/invalid dependency paths where safely testable.
9. Unity import/compile, reference, no-new-debt, scope, and scene serialization audits pass.
10. REC-006 disposition reflects stabilized lifecycle but remains open if broad composition debt persists; REC-008 remains open unless separately migrated.

## 33. Characterization conclusion

Production serialized ownership is established for both SceneRoots. Normal runtime behavior has prior successful evidence, but current `Ready` means R2 in both scenes. OpenWorld lifecycle is initiated by a broad builder that ignores root failure; Duel root reports Ready before runtime builder `Start` and cannot observe later failure. Scene-local singleton cleanup and static session/fallback conventions add P1 lifecycle risk without reopening F1.4 authority.

REC-006 advances to **CHARACTERIZED**. REC-008 remains **TRANSITIONAL / OPEN**; REC-004 and REC-005 remain **CLOSED**. No P0 defect or need for production modification was found. The evidence supports the four-slice S1.5 plan above.
