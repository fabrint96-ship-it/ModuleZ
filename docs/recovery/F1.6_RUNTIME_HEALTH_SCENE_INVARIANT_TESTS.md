# F1.6 Runtime Health and Scene Invariant Tests

## 1. Scope

S1.6-04 adds focused PlayMode runtime-health coverage for the production OpenWorld and Duel scenes, session lifecycle, scene-local ResultManager teardown, repeated loads, and persistence safety. It does not automate gameplay, Boot, navigation, results, or saving.

## 2. Baseline

Implementation started from `develop` at `323f54c4143d69f834fd3180c86e461837abd05d`. S1.6-01 through S1.6-03 were integrated. The only unrelated working-tree item was untracked `.vscode/`.

## 3. Relationship to S1.6-03 static ratchets

The 32 L0 static ratchets continue guarding source and serialized topology. These L2 tests add actual scene-loading and runtime-object evidence. Neither layer is represented as replacing the other.

## 4. Assembly-CSharp limitation

`ModuleZ.PlayModeTests` cannot directly reference production types compiled into predefined `Assembly-CSharp`. No production asmdef or assembly migration was introduced. Tests therefore resolve production types at runtime.

## 5. Runtime contract probing policy

`RuntimeContractProbe` resolves fully qualified public production types and reads or invokes only public fields, properties, and methods. It does not inspect private/internal members, backing fields, or hidden lifecycle functions and never mutates private state. Unity object enumeration, scene APIs, names, tags, and built-in components supply the remaining observations.

## 6. Production scene load strategy

Tests load only `Assets/ModuleZ/Scenes/OpenWorld.unity` and `Assets/ModuleZ/Scenes/Duel.unity` with `SceneManager.LoadSceneAsync(..., Single)`. Boot is intentionally excluded. Test setup and teardown destroy only root objects belonging to a loaded production scene; Unity Test Framework's generated runner scene is not unloaded.

## 7. State-driven wait strategy

Scene load completion is awaited through `AsyncOperation.isDone`. Root readiness is awaited through the public `State` property until its value is `Ready`. Runtime assertions execute only after this public R3 boundary.

## 8. Timeout policy

Scene loading and R3 waits each have a 20-second realtime timeout. A readiness timeout reports active scene path, root count and states, plus camera/listener counts for OpenWorld or runtime-root/ResultManager counts for Duel.

## 9. Setup/teardown isolation

Every fixture normalizes `Time.timeScale`, clears the public Duel session, destroys loaded production-scene root objects, waits for deferred destruction, verifies the session inactive invariant, and verifies `Duel3DResultManager.Instance` is null. Tests create no DDOL object, PlayerPrefs value, file, or test scene asset.

## 10. Persistence safety

Before scene execution, the local ModuleZ profile's `modulez_save.json` and `module_z_settings.json` were fingerprinted by existence, byte length, UTC modification time, and SHA-256. After the individual and combined runtime runs, every attribute remained identical for both files. No profile file was created, deleted, or modified.

## 11. OpenWorld runtime invariants

Three focused tests cover RH-OW-001 through RH-OW-008: successful production scene load; one root; public Ready/R3 state; one active Camera; one active `MainCamera` object with that Camera; one active AudioListener; one third-person controller; public root-reference coherence; and stability over ten additional frames.

## 13. Camera ownership evidence

## 14. AudioListener ownership evidence

## 15. ThirdPersonCamera evidence

## 16. Duel runtime invariants

## 17. Duel R3 evidence

## 18. Direct fallback evidence

Seven expected warnings corresponded to seven direct Duel loads; no warning was blanket-suppressed.

## 19. ResultManager lifecycle evidence

At Duel R3, exactly one live `Duel3DResultManager` existed beneath the single runtime root and public static `Instance` referenced that component. Destroying the production scene roots and yielding for deferred destruction left zero scene managers and a null public `Instance`.

## 20. Session lifecycle tests

RH-SESSION-002 uses public `StartDuel` with an existing valid enum value and isolated payload, verifies publication, then verifies complete reset. RH-SESSION-003 proves direct fallback never activates the session through R3 or teardown. No navigation or save side effect is triggered.

## 21. Repeat-load isolation

RH-ISO-001 loads and tears down OpenWorld twice and reasserts singular ownership. RH-ISO-002 loads and tears down Duel twice, verifies a fresh ResultManager instance ID, singular runtime/manager ownership, inactive session, and final cleared instance.

## 29. Known limitations

They do not inspect the third-person camera's private target, simulate input, exercise NPCs, execute Duel turns, resolve outcomes, navigate back to OpenWorld, or test save behavior. Direct fallback uses the canonical Legacy default payload rather than a normal active-session transition.
