# F1.5 Duel Readiness and ResultManager Migration

## 1. Scope

S1.5-03 makes `DuelSceneRoot` readiness reflect successful Duel runtime composition and stabilizes the scene-local `Duel3DResultManager.Instance` lifetime. Gameplay, result authority, session semantics, and scene composition are not redesigned.

## 2. Baseline

The implementation is based on develop commit `fefda0c0a85145ba5149d1cf5d272245e8adc00b`, containing the closed S1.5-01 and S1.5-02 work.

## 3. Problem statement

Before this slice, `DuelSceneRoot` reported `Ready` after the runtime GameObject and context-aware builder existed (R2). Unity invoked `Duel3DRuntimeBuilder.Start()` later to perform gameplay composition, so exceptions and `Duel3DResultManager.Initialize(...)` rejection could leave the root falsely ready with a partial runtime. `Duel3DResultManager.Instance` also lacked destruction cleanup.

## 4. Pre-slice Duel lifecycle

`DuelSceneRoot.Start()` called `DuelBootstrap.TryCreateRuntime(...)`; the bootstrap resolved one accepted `DuelContext`, created `Duel3D_Runtime`, added and initialized the builder, then returned. The root became `Ready`. Later, builder `Start()` called the void `BuildDuel3D()` method independently.

## 5. Target Duel lifecycle

The production flow is now:

`DuelSceneRoot.Start()` → `Initializing` → `DuelBootstrap.TryCreateRuntime(...)` → configured builder at R2 → `Duel3DRuntimeBuilder.TryBuild(...)` → `Ready` or cleanup plus `Failed`.

## 6. SceneRoot ownership

`DuelSceneRoot` remains the lifecycle authority. It stays `Initializing` while bootstrap creation and runtime composition execute. It assigns `RuntimeObject` and `RuntimeBuilder` only after `TryBuild` succeeds and emits the sole lifecycle-ready log.

## 7. Bootstrap responsibility

`DuelBootstrap` still resolves the accepted context, creates the scene-owned `Duel3D_Runtime` child, adds `Duel3DRuntimeBuilder`, and calls `Initialize(context)`. It no longer logs runtime creation as lifecycle success. Its existing creation/context-rejection cleanup remains intact.

## 8. Builder responsibility

`Duel3DRuntimeBuilder` remains the broad gameplay composition builder. It no longer owns a Unity `Start()` lifecycle entry and cannot make the scene root ready.

## 9. Builder API

`TryBuild(out string failureReason)` explicitly reports composition success or failure. It rejects a missing accepted context and a repeated failed/in-progress attempt. A completed build returns true without rebuilding. The guard is per instance; no static lifecycle state is introduced.

## 10. R3 readiness contract

`DuelSceneRoot.State == Ready` now means the normal composition sequence completed: accepted-context projection, match configuration, rival profile, camera/orbit setup, arena and music, materials and board, owned board roots, AI, match resolver and subscription, accepted-context ResultManager initialization, HUD, introduction/personality path, pause controller, result visuals, feedback manager, preview/HUD refresh, and ambient-comment scheduling.

This is R3. It does not claim that a turn, AI action, result, or visual effect has been exercised (R4).

## 11. Initialization sequence

The prior successful-path order is preserved. The only ownership change is that the root synchronously requests composition before accepting runtime ownership and declaring readiness.

## 12. Failure propagation

A missing context, duplicate attempt, caught composition exception, or ResultManager rejection makes `TryBuild` return false with a reason. The root deactivates and schedules destruction of `Duel3D_Runtime`, retains null public runtime references, changes to `Failed`, and logs one root-boundary failure.

## 13. Exception boundary

The main composition boundary catches exceptions and reports `<stage> failed: <message>`. It does not emit a duplicate fatal log before returning the failure.

## 14. ResultManager rejection behavior

`Duel3DResultManager.Initialize(acceptedContext)` rejection is now an explicit failed build rather than an early void return. Consequently, the root cannot remain `Ready` after rejection.

## 15. ResultManager Instance lifetime

`Duel3DResultManager.OnDestroy()` clears `Instance` only when the destroyed component is the registered instance. The manager remains scene-local and non-DDOL. Pause-menu abandon continues using `Instance` solely as an access mechanism; accepted `DuelContext` plus `DuelResult` remain result authority.

## 16. Duplicate ResultManager behavior

The pre-slice duplicate guard destroyed `gameObject`. Because the normal manager is attached to the shared `Duel3D_Runtime`, that behavior could destroy the entire runtime if a duplicate component were ever added there. The guard now destroys only the duplicate component and preserves the authoritative instance and shared runtime object.

## 17. Runtime cleanup

On failed composition, the root deactivates and destroys the top-level runtime child. This disables `Update()` immediately and removes attached builder/controllers/managers when destruction completes. Root public runtime references are assigned only after success.

## 18. Runtime child ownership

The board, cubes, preview, forbidden, and city-arena top-level objects are now parented under `Duel3D_Runtime` while preserving world transforms. They therefore participate in failed-runtime cleanup and normal scene-owned destruction. The existing scene-authored camera/light and any presentation objects intentionally created elsewhere are not broadly restructured.

## 19. MatchResolver subscription lifecycle

The builder subscribes `HandleMatchFinished` to its scene-local resolver. `OnDestroy` now unsubscribes explicitly. Both normally share the runtime lifetime, but explicit cleanup prevents the delegate from surviving an unusual asymmetric component teardown.

## 20. Direct-scene fallback preservation

Direct Duel scene entry is unchanged: only when no active session exists, bootstrap constructs one transitional context from the existing Legacy fallback and feeds it through the same builder initialization and `TryBuild` path.

## 21. DuelResult flow preservation

Victory, defeat, abandon, Draw-to-Defeat mapping, rematch policy, compatibility flags, save-before-clear/navigation ordering, delays, and OpenWorld return code are unchanged. No new result authority was introduced.

## 22. Camera/audio invariants

The existing Duel camera and AudioListener composition code is unchanged. This slice adds no Camera, AudioListener, or DDOL ownership path and does not alter F1.3 OpenWorld ownership.

## 23. REC-006 impact

REC-006 remains **IN_PROGRESS / PARTIALLY_MIGRATED**. Both OpenWorld and Duel SceneRoots now own readiness, while their builders remain broad procedural composition objects.

## 24. REC-008 impact

REC-008 remains **TRANSITIONAL / OPEN**. Session stale-field and direct-scene fallback lifecycle work is deferred to S1.5-04.

## 25. Remaining lifecycle debt

- Broad Duel builder decomposition remains deferred.
- Scene-authored camera/light and presentation-created objects are not converted into a transactional ownership model.
- Missing `ModuleZSceneController` after result application still leaves a resolved Duel loaded.
- Direct-scene fallback and stale session-field semantics remain for S1.5-04.
- Gameplay operation requires owner R4 evidence.

Scenes, OpenWorld, Packages, and ProjectSettings are unchanged.

## 30. Deviations

Runtime child parenting was included as narrow lifecycle cleanup: the five newly created top-level board/arena objects now belong to `Duel3D_Runtime`, with world transforms preserved. The unsafe duplicate-manager guard was narrowed from destroying the shared GameObject to destroying only the duplicate component. No scene serialization change was required.

## 31. Conclusion

The root now represents R3 composition readiness, builder failure is explicit, failed runtime gameplay is disabled and cleaned up best-effort, and ResultManager scene-local instance lifetime is safe across Duel reloads. R4 behavior remains subject to mandatory owner validation.
