## 6. DuelContext authority

`DuelStarterInteractable` is the sole normal intent producer. It derives rival from the configured interactable, rematch from progression, and return position from that rival transform. The readonly context contains only those three facts. The interactable does not independently perform the Legacy write cluster.

## 7. DuelTransitionBridge authority

`Begin` is the sole normal pre-Duel compatibility projection boundary and calls `ModuleZDuelSessionState.StartDuel`. `CompleteAfterDelay` preserves the 1.5-second delay and existing navigation. Both operations are stateless. Repository search finds no other production `LoadDuel()` caller and no other `StartDuel(...)` caller.

## 8. Duel startup accepted-context authority

For normal entry, `DuelBootstrap` checks `HasActiveDuel` and constructs one accepted context from the bridge-projected session transport. It configures `Duel3DRuntimeBuilder` immediately after `AddComponent`, before `Start`. The builder never reads `PendingDuelRival` or session fields. Its synchronous initial projections make remaining `CurrentDuelRival` runtime presentation/configuration readers compatibility consumers; none chooses startup intent independently.

## 9. DuelResult authority

`HandleMatchFinished` maps the runtime result and constructs `DuelResult` with `acceptedContext.RivalId`. `AbandonDuel` constructs the same contract from the initialized context. `Duel3DResultManager` contains no session-rival, current-rival, or current-rematch authority reads.

## 10. DuelResultBridge authority

The fieldless bridge validates the outcome, rival enum value, processor, and exact `result.RivalId == acceptedContext.RivalId` identity before invoking one compatibility processor. A rejected result applies no side effects and no fallback rival is selected.

## 15. Rematch call graph

The entry producer derives `IsRematch` from `ModuleZRivalProgression.IsRivalDefeated`, places it in `DuelContext`, and the bridge projects it to transport. Bootstrap accepts it once. All victory/defeat/abandon rematch counters and message choices use `acceptedContext.IsRematch`; no result branch rereads Legacy rematch state.

## 16. Repeat-Duel/stale-state analysis

On return, OpenWorld consumes the compatibility return position and pending message, then clears `PendingOpenWorldMessage`, `LastDuelResultMessage`, and `ReturningFromDuel`. The session is already inactive. A subsequent rival interaction constructs a fresh context and `StartDuel` overwrites all transport fields before loading Duel. Stale session rival/return values and the previous `PendingDuelRival` cannot control normal entry because `HasActiveDuel` is set and all relevant fields are overwritten from the new context. Owner evidence confirms a second Duel and correct rival with no stale result.

## 18. Session-state audit

`StartDuel` sets `HasActiveDuel = true` and overwrites rival, rematch, and return position from context. `Clear` sets `HasActiveDuel = false` and `IsRematch = false`; `RivalId` and `ReturnPosition` remain stale. Normal Bootstrap checks `HasActiveDuel` before reading them, and the next `StartDuel` overwrites them, so stale values are non-authoritative transitional debt. `IsRematch` does not remain stale.

## 19. Result-flag audit

The four flags are not serialized in `ModuleZSaveData`; `LoadGame` only normalizes them. `DuelCompleted` is still read by `DuelPauseMenuController` to stop pause interaction after resolution. `DuelWasCancelled`, `DuelWasLost`, and `DuelWasAbandoned` have no production readers and are write/reset-only category-I cleanup candidates. They are not authority and are retained for F1.7 or a focused later cleanup.

## 20. Return-to-OpenWorld audit

Normal return position originates in `DuelContext`, is projected into session and `OpenWorldReturnPosition`, is accepted again at startup, and is synchronously reprojected from the accepted context. Save persists that compatibility position before session clear. The OpenWorld builder reads it only when `ReturningFromDuel` is true. The pending message is displayed, then pending/last messages and the marker are cleared once. The position itself remains stale/persisted, but the cleared marker prevents it from controlling a normal spawn; a new Duel overwrites it.

## 21. LastDuelResultMessage audit

`LastDuelResultMessage` is written alongside `PendingOpenWorldMessage` in all result branches, then cleared by OpenWorld without any meaningful read. It is duplicated, write-only presentation state and a category-I removal candidate. `PendingOpenWorldMessage` is the actual required presentation compatibility path. No deletion is made in this verification slice.

## 22. Direct-scene fallback audit

With no active session, `DuelBootstrap` constructs exactly one context from default/Legacy `PendingDuelRival`, `CurrentDuelIsRematch`, and `OpenWorldReturnPosition`; defaults yield Madrid, non-rematch, and the default/persisted return position. The same builder/result path then uses this accepted context. It cannot contaminate normal production because normal bridge entry sets `HasActiveDuel` and overwrites all session facts. Static structure and Unity compilation validate the path; direct-scene runtime execution was **NOT_TESTED**. It remains category F and transitional.

## 23. ResultManager.Instance audit

`Duel3DResultManager.Instance` is a pre-existing scene-local static component reference. The builder owns a direct instance reference for match results; only `DuelPauseMenuController` uses `Instance` to reach `AbandonDuel`. The manager is not DDOL, stores context/result only on the scene instance, and does not create cross-scene state or competing authority. It is not a REC-005 blocker, but is lifecycle/dependency debt for F1.5.
