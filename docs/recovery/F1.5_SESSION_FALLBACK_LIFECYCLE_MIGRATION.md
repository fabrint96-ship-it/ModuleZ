# F1.5 Session and Fallback Lifecycle Migration

## 1. Scope

S1.5-04 stabilizes `ModuleZDuelSessionState` activation/clearing and makes the transitional direct-Duel-scene fallback explicit. It does not redesign `DuelContext`, result processing, gameplay, persistence, or navigation architecture.

## 2. Baseline

The implementation is based on develop commit `e1163ca71599af4ffe082da505b9100dd66c4179`, containing the closed F1.4 recovery and S1.5-01 through S1.5-03.

## 3. Problem statement

An inactive session retained stale `RivalId` and `ReturnPosition`; `StartDuel` published `HasActiveDuel` before its payload; fallback resolution was embedded in one method without an execution diagnostic; transition-load and fatal root initialization failures could leave a phantom active session.

## 4. Session pre-slice state

`StartDuel` set active first and payload afterward. `Clear` reset only `HasActiveDuel` and `IsRematch`. Repository-wide consumers read `RivalId`, `IsRematch`, and `ReturnPosition` only inside the bootstrap branch guarded by `HasActiveDuel`.

## 5. Session invariant

`HasActiveDuel == false` now means there is no meaningful active-session payload: `RivalId == default(ModuleZRivalId)`, `IsRematch == false`, and `ReturnPosition == Vector3.zero`. Because the enum has no neutral member, the default rival value is explicitly non-authoritative while inactive.

## 6. Session lifecycle

`INACTIVE` → `StartDuel` writes payload then activates → bootstrap copies payload into one accepted `DuelContext` → runtime uses that context → result side effects and save → `Clear` → `INACTIVE` with neutralized payload.

## 7. StartDuel semantics

`StartDuel` assigns `RivalId`, `IsRematch`, and `ReturnPosition` before publishing `HasActiveDuel = true`. Validation remains owned by `DuelTransitionBridge`; session state does not become a second policy authority.

## 8. Clear semantics

`Clear` resets all four session fields. It does not mutate `ModuleZGameState`, progression, save data, messages, or navigation.

## 9. Clear idempotency

Every assignment is deterministic and unconditional, so clearing an active, already-cleared, or never-activated fallback session produces the same inactive state without error.

## 10. Normal production context resolution

When `HasActiveDuel` is true, `DuelBootstrap.TryResolveActiveSession` creates one context exclusively from session `RivalId`, `IsRematch`, and `ReturnPosition`. This branch retains priority and emits no fallback warning.

## 11. Direct-scene fallback context resolution

When no active session exists, `TryResolveDirectSceneFallback` creates one context from `ModuleZGameState.PendingDuelRival`, `CurrentDuelIsRematch`, and `OpenWorldReturnPosition`. The method is private, scene-local in behavior, and explicitly transitional.

## 12. Production/fallback matrix

| Property | Normal production | Direct-scene fallback |
|---|---|---|
| Active session | Yes | No |
| Context source | `ModuleZDuelSessionState` | Legacy `ModuleZGameState` fields |
| Fallback warning | No | Yes, once per bootstrap resolution |
| Session active during Duel | Yes | No artificial activation |
| Result `Clear` | Yes | Safe and idempotent |

## 13. Fallback validation

Both branches validate `ModuleZRivalId` with `Enum.IsDefined`. Invalid fallback input returns `false` with `Direct-scene fallback rival is invalid.` and flows into the existing SceneRoot failure lifecycle. No rival is silently substituted.

## 14. Fallback diagnostics

Fallback use emits one warning: `[ModuleZ] DuelBootstrap using transitional direct-scene fallback.` Normal active-session entry does not execute this log.

## 15. Fallback authority boundary

Fallback does not call `StartDuel`. Once bootstrap creates the accepted context, `Duel3DRuntimeBuilder.Initialize(context)` and `TryBuild` use that accepted context; the builder does not re-read fallback fields.

## 16. Transition-load failure behavior

If delayed transition validation fails or `ModuleZSceneController.Instance` is unavailable, `DuelTransitionBridge.CompleteAfterDelay` clears session state before logging the existing error. This prevents a phantom active Duel. Legacy `ModuleZGameState` projections made by `Begin`, including the historically early `ReturningFromDuel` value, remain compatibility debt and are not broadened here.

## 17. Bootstrap/root initialization failure behavior

`DuelSceneRoot.Fail` occurs only during initialization and now clears session state before entering `Failed`. Runtime cleanup from S1.5-03 still deactivates/destroys a created runtime. No result, progression, or save has occurred at this point. No recovery navigation is invented.

## 18. Session cleanup ownership

Normal completed results retain their existing `Duel3DResultManager` calls to `Clear` after save. Pre-load failures are cleared by the transition bridge. Fatal scene-initialization failures are cleared by the scene root. All use the same idempotent session operation.

## 19. Legacy GameState payload audit

| Field | Classification | Evidence |
|---|---|---|
| `PendingDuelRival` | ACTIVE_COMPATIBILITY / FALLBACK_ONLY read | Bridge projects it; direct-scene fallback reads it; accepted runtime does not. |
| `CurrentDuelRival` | ACTIVE_COMPATIBILITY | Projected from accepted context and consumed by existing config, audio, arena, HUD, and comments. |
| `CurrentDuelIsRematch` | ACTIVE_COMPATIBILITY / FALLBACK_ONLY read | Result compatibility and direct-scene fallback; accepted normal result policy uses context. |
| `OpenWorldReturnPosition` | ACTIVE_COMPATIBILITY / FALLBACK_ONLY read | Save/OpenWorld return behavior and direct-scene fallback; normal origin is accepted context. |

These fields are not removed. Their broader disposition remains REC-008 work.

## 20. Return/result flag audit

`ReturningFromDuel`, `DuelCompleted`, `DuelWasCancelled`, `DuelWasLost`, `DuelWasAbandoned`, `PendingOpenWorldMessage`, and `LastDuelResultMessage` are unchanged compatibility/presentation fields. OpenWorld consumes the return/message state after successful composition. Failed pre-load projection may leave non-session Legacy flags, documented as remaining debt.

## 21. Result-flow preservation

`Duel3DResultManager`, `DuelResultBridge`, progression, statistics, messages, save-before-session-clear ordering, return delays, Victory, Defeat, Abandon, rematch, and Draw-to-Defeat mapping are unchanged.

## 22. REC-008 impact

REC-008 becomes **PARTIALLY_MIGRATED / STABILIZED**. Session activation and inactive payload semantics are deterministic, while Legacy `ModuleZGameState` compatibility fields remain.

## 23. REC-006 impact

REC-006 remains **IN_PROGRESS / PARTIALLY_MIGRATED**. This slice does not decompose scene builders.

## 24. Remaining lifecycle debt

- Legacy GameState compatibility payload and result/return flags remain.
- A failed pre-load transition clears session state but does not roll back every Legacy projection.
- Direct-scene fallback remains transitional developer compatibility.
- No navigation recovery is introduced after fatal Duel scene initialization.
