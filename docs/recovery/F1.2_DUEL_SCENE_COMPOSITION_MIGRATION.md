# F1.2 — Duel Scene Composition Migration

Slice: `S1.2-02`
Status: implementation and owner-run manual runtime validation complete

## Scope

This recovery slice changes only the production `Duel.unity` composition. It does not change Duel rules, AI, input, UI, persistence, progression, or the transitional cross-scene state contract.

## Composition before

```text
Duel.unity
└── Duel3D_DebugBootstrap
    └── Duel3DDebugBootstrap
        └── runtime-created Duel3D_Runtime
            └── Duel3DRuntimeBuilder
```

The production scene serialized the development adapter. That adapter could inject a debug rival, reset result flags, and remove objects by name before delegating to the production boundary.

## Composition after

```text
Duel.unity
└── DuelSceneRoot
    ├── DuelSceneRoot
    └── DuelBootstrap
        └── runtime-created Duel3D_Runtime
            └── Duel3DRuntimeBuilder
```

`DuelSceneRoot.bootstrap` is explicitly serialized to the colocated `DuelBootstrap`. The root has an identity transform so the owned runtime retains its existing world-space origin. `DuelSceneRoot.Start()` remains the single initialization entry, and its lifecycle guard prevents repeat initialization.

## Production/debug separation

`Duel.unity` no longer serializes `Duel3DDebugBootstrap`, and the `Duel3D_DebugBootstrap` GameObject is absent. S1.2-03 subsequently proved the adapter had no serialized reference, source consumer, or documented active debug workflow and removed the unreachable source plus its `.meta`. Production code does not depend on it.

The production composition does not inject a debug rival and does not perform cleanup by object name.

## Legacy behavior preserved

The runtime implementation remains `Duel3DRuntimeBuilder`. The production bootstrap owns an explicit reference to the created `Duel3D_Runtime`, and `DuelSceneRoot` records that runtime and its builder when initialization succeeds.

## Transitional state dependencies

Until F1.4 introduces `DuelContext` and `DuelResult`, startup continues to validate the existing state in this order:

1. `ModuleZDuelSessionState` for the normal OpenWorld-to-Duel transition.
2. The documented `ModuleZGameState.PendingDuelRival` legacy fallback.

No additional source of truth or mutable global state is introduced.
