# F1.5 OpenWorld Readiness Migration

## 1. Scope

S1.5-02 makes `OpenWorldSceneRoot` the production lifecycle authority for OpenWorld composition. It changes lifecycle ownership and failure reporting only; it does not decompose the procedural builder or redesign gameplay.

## 2. Baseline

The implementation is based on develop commit `8fad343f26d1331b546893163ddf0ed0d544d7ba`, which includes the closed S1.5-01 characterization. `OpenWorld.unity` already serializes one `OpenWorldRuntimeBuilder` and one `OpenWorldSceneRoot` on `OpenWorld_Runtime`.

## 3. Problem statement

Before this slice, `OpenWorldRuntimeBuilder.Start()` independently began composition, dynamically added a missing root, ignored the result of `OpenWorldSceneRoot.Initialize(...)`, and continued success logging and pending-message work after a rejected root initialization. Root `Ready` represented owned references at approximately R2, not successful completion of the builder's composition boundary.

## 4. Pre-slice lifecycle

`OpenWorldRuntimeBuilder.Start()` resolved or created a root, built theme/UI/music/player/camera content, called the root with references, then unconditionally began message handling and logged success. Exceptions were not translated into root lifecycle state, and direct top-level partial objects were not cleaned up.

## 5. Target lifecycle

The production path is now:

`OpenWorldSceneRoot.Start()` → `Initializing` → `OpenWorldRuntimeBuilder.TryBuild(...)` → ownership validation → `Ready` or `Failed`.

There is no builder `Start()` entry point and no dynamic `AddComponent<OpenWorldSceneRoot>()` fallback.

## 6. Ownership change

`OpenWorldSceneRoot` owns lifecycle state and invokes the same-object builder. `[RequireComponent(typeof(OpenWorldRuntimeBuilder))]` expresses the serialized composition requirement. The builder remains responsible for procedural construction but cannot mark the scene ready.

## 7. Builder API change

`TryBuild` returns a Boolean result, an explicit failure reason, and the created Player, Camera, AudioListener, and `ModuleZThirdPersonCamera` references. A per-instance attempt guard rejects a second build without introducing static or cross-scene state.

## 8. SceneRoot lifecycle semantics

- `Uninitialized` may begin one initialization.
- `Initializing` rejects re-entry.
- `Ready` is stable and a repeated `Initialize()` call returns true without rebuilding.
- `Failed` is stable and does not silently retry.

The root assigns its public ownership references only after successful composition and ownership validation.

## 9. R3 readiness contract

`Ready` now represents R3 for the builder boundary: theme data was resolved; required HUD, pause, theme, and music composition calls completed; Player and gameplay Camera were created; Camera-owned AudioListener and third-person controller ownership was validated; and `TryBuild` returned success without an exception.

R3 does not claim a rendered frame, completed behavior from every component `Start()`, exercised input, or user-observed gameplay. Those remain R4/runtime-validation concerns.

## 10. Failure propagation

A missing builder, rejected build, invalid required ownership reference, or caught composition exception moves the root to `Failed`. The root emits the single lifecycle-fatal diagnostic in the form `[ModuleZ] OpenWorldSceneRoot failed: <reason>`. Failure does not emit the readiness success log and does not start normal pending-message handling.

## 11. Exception handling

`TryBuild` catches exceptions at the OpenWorld composition boundary. Its failure reason includes the active high-level stage and exception message. The builder returns that evidence to the root instead of using an uncaught exception as the only lifecycle signal.

## 12. Partial-build cleanup

On failure, the builder deactivates and schedules destruction of directly referenced top-level objects it owns: the Player, gameplay Camera, and temporary PlayerBuilder host. This is best-effort cleanup. Components and children already attached by broad HUD/theme/music composition are not transactionally rolled back; that remains transitional REC-006 debt and is not hidden by a false `Ready` state.

## 13. Pending-message lifecycle

The root starts post-build pending-message handling only after setting `Ready`. Existing successful-path message selection, timeout, state clearing, and HUD refresh behavior is preserved. The existing behavior that clears pending state when the presentation HUD is unavailable after its timeout remains presentation debt outside this slice.

## 14. Camera/listener invariants

The F1.3 ownership path is unchanged: `OpenWorldGameplayCameraBuilder.Create(...)` creates one `Main Camera` with Camera, active AudioListener, and `ModuleZThirdPersonCamera`. The root validates that listener and controller belong to that Camera GameObject before accepting ownership.

## 15. Spawn behavior preservation

Player spawn selection is unchanged: `ReturningFromDuel ? OpenWorldReturnPosition : new Vector3(0f, 0.1f, -4f)`.

## 16. Runtime compatibility

Theme selection, HUD components, pause menu, music, Player construction, camera configuration, pending messages, rival HUD refresh, and OpenWorld/Duel state consumers retain their previous successful-path order and behavior. No scene, input, persistence, progression, or Duel code changed.

## 17. REC-006 impact

REC-006 is **IN_PROGRESS / PARTIALLY_MIGRATED**. The builder no longer owns lifecycle entry or readiness, but it remains a broad procedural composition builder and partial rollback is intentionally incomplete.

## 18. REC-008 impact

REC-008 remains **TRANSITIONAL / OPEN**. Legacy return flags and pending-message fields remain compatibility state; this slice does not decompose `ModuleZGameState`.

## 19. Remaining lifecycle debt

- Broad builder decomposition remains deferred.
- HUD/theme/music objects created before a late failure are not transactionally removed.
- Pending-message timeout still clears compatibility state when its target HUD is unavailable.
- R4 gameplay operation requires owner Play Mode evidence.
- Duel lifecycle, ResultManager lifetime, session stale fields, and direct-scene fallback belong to later F1.5 slices.

## 20. Static validation

**PASS.** Repository inspection confirms one root-owned entry, no builder `Start()`, an explicit build result and failure reason, no dynamic root addition, post-build message start only after `Ready`, and root reference assignment only after validation. The diff adds no global lifecycle state, singleton, DDOL call, object lookup, legacy Input consumer, Core-to-OpenWorld dependency, or production debug dependency. `OpenWorld.unity`, `Packages/`, and `ProjectSettings/` are unchanged.

## 21. Runtime validation

Owner validation OW-01 through OW-06 is **NOT_TESTED** for this implementation commit and is mandatory before integration. OW-07 is optional and **NOT_TESTED**. Console error count and visible regressions are **UNKNOWN** until that run. Automated evidence is not substituted for runtime results.

## 22. Tests

**NOT_APPLICABLE — no ModuleZ project test assembly exists.** No test framework was introduced for this narrow lifecycle migration.

## 23. CI

**NOT_DETECTED.** The repository contains no `.github/workflows` directory at this baseline. PR check state is reported separately after PR creation.

## 24. Deviations

No scene change was required. Cleanup is deliberately limited to directly referenced top-level runtime objects; complete transactional rollback would exceed this slice. Unity 6000.3.13f1 batchmode import/compile completed with return code 0 and no compilation, import, Missing Script, or serialization errors. It reported existing compiler warnings outside this slice and no tracked Asset Database changes beyond the two edited scripts.

## 25. Conclusion

The OpenWorld root is now the sole production lifecycle authority and its `Ready` state represents successful R3 completion of the existing builder boundary. Runtime R4 behavior remains subject to the required owner validation.
