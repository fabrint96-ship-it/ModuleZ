# F1.6 Static Architecture and Foundation Ratchets

## 1. Scope

S1.6-03 adds repository-text validation for the recovered F0/F1 architecture. It adds no runtime behavior, scene content, Unity package, ProjectSettings, or CI change.

## 2. Baseline

The reviewed baseline is `develop` at `80cff45d16981eb28eb3c7c88614cd37ca8c8864`. S1.6-01 and S1.6-02 are integrated. The baseline file is deliberately fixed to that commit and is never rewritten by validation.

## 3. Ratchet philosophy

Recovered invariants are checked directly where repository structure makes the answer deterministic. Accepted legacy debt is recorded by stable file/symbol or file/expression identities. Existing or reduced debt passes; a new unreviewed occurrence fails or warns according to the rule.

## 4. Exact vs heuristic semantics

`STATIC_EXACT` checks assert a structural fact that the validator can decide deterministically. `STATIC_HEURISTIC` checks identify architectural risk through conservative source patterns and are never described as semantic proof.

## 5. Gating model

Thirty checks gate the command. All exact checks gate. New object-lookup and clear Core dependency occurrences also gate despite their heuristic classification because their matched forms are strong policy signals. Global mutable-state and visible-text candidates warn and do not gate. `FAIL` on any gating check makes the process nonzero; `WARN` alone does not.

## 6. Validator structure

`Tools/Validation/Static/Invoke-ModuleZStaticValidation.ps1` resolves the repository, reads the reviewed baseline, runs `STATIC-001` through `STATIC-032`, prints concise results, and emits JSON and a log. It scans production under `Assets/ModuleZ` while excluding tests and non-production documentation/tool/artifact areas.

## 7. Result schema

`artifacts/validation/static-results.json` contains schema and validator versions, UTC timestamp, repository root, baseline commit, overall status, summary counts, and every check's ID, category, classification, status, gating flag, message, evidence, and baseline use. Overall is `FAIL` only when a gating check fails.

## 8. Build Settings checks

`STATIC-001` parses `ProjectSettings/EditorBuildSettings.asset` and requires the enabled order to be exactly Boot, OpenWorld, Duel with no additional enabled scene.

## 9. Scene ownership checks

`STATIC-003`, `004`, and `009` structurally guard OpenWorld YAML against an authored Camera, Main Camera/MainCamera tag, authored AudioListener, and duplicate/missing serialized `OpenWorldSceneRoot`. `STATIC-010` and `011` require one serialized `DuelSceneRoot`, one `DuelBootstrap`, and no debug bootstrap. `STATIC-012` rejects test-script GUIDs in production scenes.

## 10. DebugBootstrap check

`STATIC-002` searches production source and serialized assets for the former class/object names and recovered legacy script GUID while excluding docs, tests, and tools. Current result: zero production references.

## 11. Camera creation-path check

`STATIC-005` requires the one OpenWorld delegation from `OpenWorldRuntimeBuilder` to `OpenWorldGameplayCameraBuilder.Create`, exactly one `new GameObject("Main Camera")`, and exactly one OpenWorld `AddComponent<Camera>()` in the canonical builder.

## 12. AudioListener creation-path check

`STATIC-006` requires exactly one OpenWorld `AddComponent<AudioListener>()`, in `OpenWorldGameplayCameraBuilder`, and retains its ownership-validation evidence.

## 13. Builder lifecycle checks

`STATIC-007` and `008` require explicit `TryBuild` entry points and reject parameterless `Start()` lifecycle ownership in the OpenWorld and Duel runtime builders.

## 14. DDOL baseline

`STATIC-013` ratchets five reviewed `DontDestroyOnLoad` occurrences. `STATIC-015` separately requires zero such calls in OpenWorld and Duel3D scene-local runtime code. New unallowlisted occurrences fail.

## 15. Legacy Input baseline

`STATIC-014` records 31 reviewed legacy Input API occurrences, grouped into 16 stable file/API identities. Equal or lower counts pass; a new identity or count increase fails.

## 16. Object lookup baseline

`STATIC-017` records eight reviewed `FindObjectOfType`, `FindFirstObjectByType`, `FindAnyObjectByType`, and `GameObject.Find` occurrences. It is labeled heuristic; a new unreviewed occurrence fails.

## 17. Core dependency ratchets

`STATIC-018` baselines six current Core-to-OpenWorld textual namespace references across five files. `STATIC-019` has a zero Core-to-Game baseline. New clear using/qualified references fail; these remain heuristic because source-text topology is not a complete dependency graph.

## 18. Global mutable-state heuristic

`STATIC-020` compares suspicious static fields and settable static properties with the reviewed file/symbol baseline. It is intentionally non-gating and warns on growth; regex matching cannot fully determine C# mutability or architectural intent.

## 19. Hardcoded UI heuristic

`STATIC-021` examines likely UI/HUD sources for literal assignments to visible text properties. Reviewed literals are baselined; new candidates warn. Logs, IDs, tests, and non-presentation paths are outside this check, and localization correctness still requires review.

## 20. DuelContext authority ratchets

`STATIC-022` requires `DuelStarterInteractable` to create `DuelContext` and call `DuelTransitionBridge.Begin`, with the bridge projecting `StartDuel`. `STATIC-023` requires bootstrap context resolution and explicit runtime initialization, and rejects post-acceptance `PendingDuelRival` or session-payload reads in the Duel runtime builder.

## 21. DuelResult authority ratchets

`STATIC-024` requires runtime `DuelResult` construction, the result-manager contract entry, the `DuelResultBridge` call, and rival-identity validation. `STATIC-025` rejects legacy `WinDuel`/`LoseDuel` operations. `STATIC-026` requires exactly one explicit Draw-to-Defeat mapping.

## 22. Session lifecycle static guards

`STATIC-027` extracts `StartDuel` and requires rival, rematch, and return-position payload writes before `HasActiveDuel = true`. `STATIC-028` extracts `Clear` and requires the full inactive reset. `STATIC-029` requires an isolated direct-scene fallback that creates one `DuelContext` without calling `StartDuel`.

## 23. Test infrastructure ratchets

`STATIC-030` requires both S1.6-02 test asmdefs. `STATIC-031` requires test-assembly support and confines all ModuleZ asmdefs to the tests tree. `STATIC-032` requires the checked-in wrapper and its static-stage integration.

## 24. Baseline/allowlist design

`Tools/Validation/Static/ModuleZ.StaticBaseline.json` has schema version 1 and stable identities: repository-relative file plus scope/expression, domain, API, symbol list, or literal list. It avoids line-number-only identities.

## 25. Baseline update policy

The validator reads but never modifies the baseline. Any new accepted debt requires an explicit reviewed change explaining the occurrence. Debt removal needs no baseline edit and remains a pass.

## 26. Wrapper integration

`Invoke-ModuleZValidation.ps1 static` invokes the validator, preserves its nonzero exit, requires the JSON and log, parses JSON, and rejects any overall value other than `PASS`. Existing `tests` remains EditMode plus PlayMode. New `all` means static, compile, EditMode, then PlayMode.

## 27. Machine-readable artifacts

Runs write ignored artifacts to `artifacts/validation/static-results.json` and `artifacts/validation/static.log`. Generated artifacts are not source and are not committed.

## 28. Failure-propagation evidence

A temporary untracked production C# file containing a new `Input.GetKeyDown` call was added locally. `STATIC-014` failed and the wrapper returned exit code 1. The file was then removed before Unity execution and is absent from the final tree. A clean rerun returned 0 with all checks passing.

## 29. Final validation results

Final static result: 32 PASS, 0 WARN, 0 FAIL; 27 exact and 5 heuristic; 30 gating. Compile returned 0 with no compilation, import, Missing Script, or serialization errors. EditMode and PlayMode each discovered and passed one test with zero failures. The combined `tests` stage and the full `all` stage passed. `git diff --check` passed after removing Unity-generated solution-file churn.

## 30. False-positive limitations

The validator is source/serialization aware but is not a C# compiler or full Unity object model. Heuristics can miss indirect dependencies, reflection, generated code, runtime text construction, or semantically mutable objects hidden behind methods. Scene checks protect current canonical YAML topology, not runtime behavior. These limits are explicit and motivate later runtime coverage.

## 31. Deferred runtime proof

Production-scene PlayMode assertions, persistence isolation, canonical roundtrip smoke, gameplay behavior, and CI execution remain for S1.6-04 onward. Static success is not runtime-health proof.
