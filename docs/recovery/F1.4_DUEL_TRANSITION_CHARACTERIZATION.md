# F1.4 — Duel Transition Characterization and Contract Boundary

Slice: `S1.4-01`

Status: characterization complete; production migration not started

## 1. Scope

This document characterizes the current production OpenWorld → Duel → OpenWorld data-transfer pipeline from repository evidence and defines the minimum proposed `DuelContext`, `DuelResult`, and one-way compatibility bridges. It changes no production behavior, source, scene, asset, persistence schema, or runtime architecture.

## 3. Production OpenWorld → Duel call graph

```text
DuelStarterInteractable.Interact()
  -> validate rival unlocked / rematch allowed
  -> derive isRematch from ModuleZRivalProgression.IsRivalDefeated(rivalId)
  -> derive returnPosition from rival transform position + (0, 0, -3)
  -> write ModuleZGameState compatibility fields
  -> ModuleZDuelSessionState.StartDuel(rivalId, isRematch, returnPosition)
  -> Invoke(StartDuel, 1.5 seconds)
DuelStarterInteractable.StartDuel()
  -> clear pause and repeat four result-flag resets
  -> ModuleZSceneController.Instance.LoadDuel()
ModuleZSceneController
  -> SceneManager.LoadScene("Duel")
Duel.unity
  -> DuelSceneRoot.Start()
  -> DuelBootstrap.TryCreateRuntime()
  -> validate legacy startup rival
  -> create owned Duel3D_Runtime + Duel3DRuntimeBuilder
Duel3DRuntimeBuilder.Start()
  -> BuildDuel3D()
```

There is no explicit region or encounter-context transfer. `CurrentOpenWorldTheme` exists globally but is neither copied into `ModuleZDuelSessionState` nor read by Duel startup. Rival identity is the only repository-backed regional discriminator used by Duel.

## 5. Duel initialization reads

### DuelBootstrap

`HasValidLegacyStartupState` chooses one rival solely for enum validation:

```text
if ModuleZDuelSessionState.HasActiveDuel
    validate ModuleZDuelSessionState.RivalId
else
    validate ModuleZGameState.PendingDuelRival
```

It does not retain or pass that value to `Duel3DRuntimeBuilder`.

### Duel3DRuntimeBuilder

At the start of `BuildDuel3D`:

1. If `HasActiveDuel` is true, copy session `RivalId`, `IsRematch`, and `ReturnPosition` into `CurrentDuelRival`, `CurrentDuelIsRematch`, and `OpenWorldReturnPosition`.
2. Unconditionally assign `CurrentDuelRival = PendingDuelRival`.
3. Build match config, rival profile, arena, audio, UI, dialogue, and visuals from `CurrentDuelRival`.
4. Use progression/statistics globals to derive AI scaling.
5. Mark the selected rival's personality-completed flag during initialization.

The personality flag mutation is an existing Duel-entry side effect. It is neither transition input nor result data.

## 6. Actual precedence and fallback behavior

| Concept | Actual behavior when stores agree | Actual behavior when stores disagree |
| --- | --- | --- |
| Bootstrap rival validation | Session rival when active; otherwise pending rival | An active valid session permits startup even if pending rival differs or is invalid |
| Runtime rival/config/presentation | Session rival is copied, then pending rival overwrites it | `PendingDuelRival` wins unconditionally |
| Result rival for victory progression | Session rival when active; otherwise `CurrentDuelRival` | Active session rival wins |
| Loss/abandon result identity variable | Resolves session rival into local `defeatedRival` | The local value is not used for message construction; messages use `CurrentDuelRival` |
| Rematch | Session value copied when active; otherwise existing `CurrentDuelIsRematch` remains | Active session value wins |
| Return position | Session value copied when active; otherwise existing `OpenWorldReturnPosition` remains | Active session value wins |

Therefore a disagreement can produce a Duel presented/configured as the pending rival while victory progression is applied to the session rival. Loss/abandon messages use the runtime current rival. Normal OpenWorld entry currently writes all rival stores to the same value, masking this split authority.

No additional default is introduced by production entry. Static field initialization defaults rival values to Madrid and return position to `(0, 0.1, -4)`, so direct/invalidly prepared entry can appear valid through legacy defaults.

### Match victory/defeat/draw

```text
Duel3DMatchResolver.FinishMatch(Duel3DMatchResult)

```

Draw is explicitly collapsed into the existing loss path.

### Abandon

```text
DuelPauseMenuController.OnAbandonClicked()
  -> restore time/pause UI state
  -> Duel3DResultManager.AbandonDuel()
  -> same mutation/save/session-clear/navigation sequence
```

## 8. Duel result mutations

Common to victory, defeat, and abandon:

- runtime-local `resultResolved = true` prevents repeated processing;
- resolve a rival from active session, otherwise `CurrentDuelRival`;
- set `DuelCompleted = true` and `DuelWasCancelled = false`;
- set the outcome booleans;
- increment one total Duel statistic;
- optionally increment one rematch statistic;
- construct and write `LastDuelResultMessage` and `PendingOpenWorldMessage`;
- set `CurrentDuelIsRematch = false`;
- call `ModuleZSaveManager.SaveGame()`;
- clear session presence/rematch via `ModuleZDuelSessionState.Clear()`;
- later set `ReturningFromDuel = true`, clear pause, and load OpenWorld.

Outcome-specific mutations:

| Path | Flags | Statistics | Progression | Delay |
| --- | --- | --- | --- | ---: |
| Victory | lost `false`, abandoned `false` | `DuelsWon++`; `RematchesWon++` for rematch | Non-rematch calls `MarkRivalDefeated`; may unlock next region or complete main progression | 1.5 s |
| Defeat | lost `true`, abandoned `false` | `DuelsLost++`; `RematchesLost++` for rematch | None | 1.5 s |
| Draw | Routed to defeat path | Same as defeat | None | 1.5 s |
| Abandon | lost `false`, abandoned `true` | `DuelsAbandoned++`; `RematchesAbandoned++` for rematch | None | 0.8 s |

`MarkRivalDefeated` writes the rival defeated flag, updates Andalucía unlock state, and for Andalucía writes `MainProgressionCompleted = true`. `SaveGame` evaluates achievements, snapshots progression/statistics/personality/return data, and writes `modulez_save.json` before navigation.

`ModuleZDuelSessionState.Clear()` clears only `HasActiveDuel` and `IsRematch`. Its `RivalId` and `ReturnPosition` remain stale but inactive.

## 9. Result data versus side effects

### Result data

- normalized outcome: victory, defeat, or abandoned;
- rival identity to which the result applies.

The match resolver's draw is not a distinct current post-Duel result: it is converted to defeat before legacy result processing. Rematch and return position describe the started Duel and remain in `DuelContext`; they need not be duplicated in `DuelResult` if the result bridge receives both values.

### Side effects, not DuelResult fields

- progression flags and unlock calculation;
- total/rematch statistic increments;
- personality-completed state;
- achievement evaluation/unlocks;
- save invocation and persistence DTO writes;
- localized/display message construction and pending-message storage;
- legacy result booleans;
- session cleanup;
- pause/time restoration;
- scene navigation;
- OpenWorld player spawning, HUD refresh, and message display.

These behaviors may initially remain in existing collaborators. A data contract must describe what happened, not perform or store every downstream mutation.

## 10. OpenWorld return consumption

`OpenWorldRuntimeBuilder` consumes return state in this order:

1. Reads `CurrentOpenWorldTheme` to choose the regional theme.
2. `CreatePlayer` checks `ReturningFromDuel`.
3. If true, spawns at `OpenWorldReturnPosition`; otherwise uses `(0, 0.1, -4)`.
4. Builds the runtime camera and remaining OpenWorld composition.
5. Starts `ShowPendingOpenWorldMessageWhenReady` and waits up to two seconds for `OpenWorldMessageHUD`.
6. Reads `PendingOpenWorldMessage`; if empty, uses the theme entry message.
7. Shows the message through `OpenWorldSystemMessageHUD` when available.
8. Clears `PendingOpenWorldMessage`, `LastDuelResultMessage`, and `ReturningFromDuel`.
9. Calls `ModuleZRivalWorldHUDController.RefreshAll`, whose consumers re-read progression state.

`OpenWorldReturnPosition`, `PendingDuelRival`, `CurrentDuelRival`, result booleans, statistics, progression, and inactive session `RivalId`/`ReturnPosition` are not cleared by this return consumer. `OpenWorldReturnPosition` is also persisted by the save performed before navigation.

No new canonical runtime store is declared in this characterization. The contracts below are proposed intent/result values; S1.4 implementation must define ownership without adding another mutable global container.

## 12. Proposed DuelContext

Proposed form: immutable/value-like data passed into a narrowly scoped transition/startup handoff.

| Field | Type | Producer | Consumer | Why required | Legacy sources | Migration notes |
| --- | --- | --- | --- | --- | --- | --- |
| `RivalId` | `ModuleZRivalId` | OpenWorld rival interaction | Duel bootstrap/runtime config; result association | Selects match configuration, profile, arena, audio, dialogue, and result target | pending/current/session rival fields | Bridge writes all required legacy projections once; eliminate read-back synchronization |
| `IsRematch` | `bool` | OpenWorld progression query at interaction | Result policy and rematch statistics/messages | Current behavior distinguishes rematch counters and suppresses first-win progression | session `IsRematch`, `CurrentDuelIsRematch` | Do not re-derive inside Duel from progression because intent was decided at interaction |
| `ReturnPosition` | `Vector3` | OpenWorld rival interaction | OpenWorld return spawn compatibility | Preserves exact return location after Duel | session `ReturnPosition`, `OpenWorldReturnPosition` | Carried with context even though Duel presentation does not consume it |

No separate region/theme field is justified: current Duel startup has no such reader. No result flags, message, progression, statistics, save, or navigation data belongs in `DuelContext`.

## 13. Proposed DuelResult

Proposed outcome enum:

```text
DuelOutcome
  Victory
  Defeat
  Abandoned
```

Proposed immutable/value-like result:

| Field | Type | Producer | Consumer | Why required | Legacy destinations | Migration notes |
| --- | --- | --- | --- | --- | --- | --- |
| `Outcome` | `DuelOutcome` | Duel runtime/result boundary | result compatibility orchestration | Replaces ambiguous combinations of completed/lost/abandoned/cancelled booleans | four legacy result booleans; statistics branches | Preserve current Draw → Defeat mapping initially |
| `RivalId` | `ModuleZRivalId` | Duel runtime from accepted context | progression/message/result compatibility | Identifies the rival whose outcome is applied and prevents session/current split | defeated-rival selection and current rival | Validate it matches the accepted context; do not re-resolve from competing stores |

`IsRematch` remains input context. The result bridge should receive the accepted `DuelContext` alongside `DuelResult` rather than duplicate rematch and return data in the result. No message string, progression flags, counters, save status, or scene name belongs in `DuelResult`.

## 14. Proposed DuelTransitionBridge

Narrow responsibility:

```text
DuelStarterInteractable
  -> construct DuelContext once
  -> DuelTransitionBridge.Begin(context)
       -> validate context
       -> write required ModuleZDuelSessionState compatibility fields
       -> write required ModuleZGameState projections/reset flags
       -> request existing ModuleZSceneController.LoadDuel()
```

The bridge is an operation boundary, not a store. It must not be static mutable session state, a singleton, DDOL object, service locator, or bidirectional synchronizer. The producer supplies the context; the bridge performs one-way legacy projection and navigation. S1.4-02 should move the current clustered pre-Duel writes here without changing their values or timing beyond a deliberately reviewed single invocation.

## 15. Proposed DuelResultBridge

Narrow responsibility:

```text
Duel runtime
  -> map match/abandon event to DuelResult
  -> DuelResultBridge.Complete(acceptedContext, result)
       -> validate result/context identity
       -> invoke preserved legacy compatibility side effects
       -> clear legacy session compatibility state
       -> request existing OpenWorld navigation
```

Initial responsibilities may include projecting the explicit outcome into legacy booleans and coordinating the existing result workflow. Progression mutation, statistics policy, achievement evaluation, save serialization, message formatting/display, and navigation implementation should remain in focused existing collaborators or explicitly invoked compatibility routines—not become fields or an ever-growing result object.

S1.4-03 should extract the current three near-duplicate result paths behind this boundary while preserving victory/defeat/abandon statistics, non-rematch progression, Draw → Defeat behavior, messages, save-before-navigation timing, session clearing, and delays.

## 16. Transitional authority rule

Required direction:

```text
new user/gameplay intent
  -> immutable DuelContext
  -> DuelTransitionBridge
  -> one-way Legacy compatibility projection
  -> Duel startup

Duel completion fact
  -> immutable DuelResult
  -> DuelResultBridge with accepted DuelContext
  -> one-way Legacy side-effect compatibility
  -> return navigation
```

Forbidden direction:

```text
Legacy store A <-> contract <-> Legacy store B
```

Contracts must be constructed once at their producer boundary. Legacy values may be populated temporarily, but must not be read back into the contract or continuously synchronized.

## 17. No-new-debt constraints

The proposed boundaries introduce no new mutable global state, static session container, singleton, DDOL state owner, service locator, global event bus, mutable ScriptableObject state, arbitrary `FindObjectOfType` injection, Core-to-OpenWorld dependency, or production debug dependency.

Contract placement must respect dependency direction. Because the current `ModuleZRivalId` type lives under OpenWorld, S1.4-02 must choose a neutral existing/lower-level contract location or explicitly account for this coupling; it must not make Core depend on OpenWorld merely for convenience.

## 21. Unknowns and unresolved questions

1. Contract namespace/assembly placement is unresolved. `ModuleZRivalId` currently resides in `ModuleZ.OpenWorld.Encounters`; moving or replacing it could affect serialization and is not authorized by this slice.
2. Repository evidence does not justify a separate region/context field. Future product requirements may, but current readers do not.
3. The desired long-term treatment of resolver `Draw` is unspecified. Current behavior must initially remain Draw → Defeat.
4. No production path sets `DuelWasCancelled = true`; whether cancellation is obsolete or future-facing is unknown.
5. `LastDuelResultMessage` has no distinct production reader beyond being cleared; whether it remains compatibility-required should be verified during implementation.
6. Session `Clear` leaves stale rival and return position. Whether S1.4 migration may clear them without affecting diagnostics/direct entry requires implementation-time validation.
7. Direct Duel scene entry currently succeeds through initialized Madrid defaults when no active session exists. Whether that compatibility must remain after contract migration requires an explicit owner decision; production normal flow does not require it.
8. The existing result manager resolves session rival but builds loss/abandon messages from current rival. Normal flow masks the mismatch; migration must preserve normal behavior while removing ambiguous authority.

## 22. S1.4-02 implementation boundary

Do not implement result migration, progression/save redesign, or remove all legacy fields in the same slice.

Implementation must explicitly resolve neutral type placement and the direct-scene-entry question before deleting fallbacks. It must add focused tests where the value contract/translation is pure-testable.
