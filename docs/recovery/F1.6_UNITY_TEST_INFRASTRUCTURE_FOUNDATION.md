# F1.6 Unity Test Infrastructure Foundation

## 1. Scope

S1.6-02 establishes the smallest reproducible Unity Test Framework foundation for ModuleZ. It proves EditMode and PlayMode discovery/execution, structured results, independent logs, exit behavior, and a local PowerShell entry point. It adds no production behavior, scene content, full regression coverage, or CI.

## 5. Assembly design

`ModuleZ.EditModeTests` uses `optionalUnityReferences: ["TestAssemblies"]` and is constrained to `Editor`. `ModuleZ.PlayModeTests` uses the same TestAssemblies support without an Editor-only constraint, allowing PlayMode discovery. Neither assembly declares production references, unsafe code, or additional packages. No production asmdef was introduced and production remains in predefined `Assembly-CSharp`.

## 6. Assembly-CSharp accessibility finding

Unity `6000.3.13f1` was tested rather than assumed. A temporary local probe added `"Assembly-CSharp"` to the EditMode asmdef and referenced `ModuleZ.Game.DuelTransition.DuelContext` from the fixture. Compilation failed with CS0234 because the production namespace was unavailable to the asmdef assembly. Merely naming the predefined assembly did not provide typed access.

The probe was reverted before the final run. The committed proof tests intentionally avoid production types. S1.6-04 cannot assume typed access from these asmdefs; it must select a supported test boundary without forcing production assembly modularization into this slice.

## 7. EditMode proof fixture

## 8. PlayMode proof fixture

## 9. Isolation model

The fixtures create no GameObject, scene object, DDOL object, coroutine outside the Test Runner, or persistent/static state. They do not alter `Time.timeScale`, PlayerPrefs, ModuleZ globals, files, production scenes, or user settings. The PlayMode fixture uses only the Test Runner's coroutine frame yield.

## 10. Persistence safety

Before execution, four existing `modulez_save.json` / `module_z_settings.json` files were inventoried across the two existing ModuleZ profiles under `AppData/LocalLow`. After all passing, failing, assembly-access, compile, EditMode, and PlayMode runs, their sizes and `LastWriteTimeUtc` values were unchanged. Final SHA-256 values were also recorded for diagnostic evidence. No save/settings file was created, deleted, or overwritten by these proof tests.

## 11. Validation wrapper

`Tools/Validation/Invoke-ModuleZValidation.ps1` supports:

- `compile`
- `editmode`
- `playmode`
- `tests` (EditMode followed by PlayMode)

It creates only generated artifacts below the ignored `artifacts/validation/` directory. It uses a Windows process wait that follows Unity's process handoff using the unique log path, so XML validation does not race a still-running Unity process.

## 12. Unity resolution

Resolution order is:

1. caller-supplied `-UnityPath`;
2. exact verified path `C:\Program Files\Unity\Hub\Editor\6000.3.13f1\Editor\Unity.exe`;
3. explicit failure if the file is absent.

The wrapper does not search for or silently select another editor version.

## 17. XML contract

PowerShell parses XML structurally. For the requested platform it requires:

1. the result file exists;
2. a `test-run` root exists;
3. the expected `ModuleZ.<Platform>Tests.dll` assembly node exists;
4. that ModuleZ assembly contains at least one `test-case`;
5. every discovered ModuleZ test has result `Passed`.

This prevents a package-owned test from masking zero ModuleZ discovery. Missing, malformed, zero-test, absent-assembly, or failed results cannot be reported as PASS.

## 18. Exit-code contract

The wrapper returns 0 only after the requested stage completes. A nonzero Unity status is propagated as the wrapper status. Unity startup failure, missing XML, invalid XML shape, missing ModuleZ assembly, zero ModuleZ tests, or any non-passed ModuleZ case without a Unity failure status returns 1. No failing condition can be converted to PASS.

## 20. Failure-propagation evidence

A temporary local change replaced the EditMode expected value `4` with `5`. Unity reported failed tests and returned exit code **2**. After the final exit contract was established, a parent process captured wrapper exit code **2**, proving propagation rather than masking. The separate Assembly-CSharp probe also demonstrated compile-stage propagation: Unity returned 1 for CS0234 and the wrapper returned nonzero. It too was fully reverted before final validation.

## 23. Known limitations

- The fixtures prove infrastructure only, not ModuleZ production invariants.
- Test asmdefs cannot currently compile against predefined `Assembly-CSharp` by adding it as an asmdef reference.
- `tests` runs both platforms but not a separate compile stage; callers needing the full validation sequence invoke `compile` and then `tests`.
- The wrapper is Windows/PowerShell and intentionally pinned to the verified editor.
- Generated artifacts are local only; there is no CI publication or coverage configuration.
- Production-scene tests, persistence isolation, and smoke automation remain deferred.

## 24. Implications for S1.6-03

Static ratchets can be implemented without typed production test access, preferably as repository/Editor validation invoked separately from these proof assemblies. S1.6-03 should preserve the current command and artifact contracts while deciding whether a future `static` stage belongs in the wrapper.

## 25. Implications for S1.6-04

Runtime scene invariants can use PlayMode scene loading and Unity component APIs, but direct compile-time production-type access needs a supported boundary. S1.6-04 must not solve that by silently introducing broad production asmdefs. Options must be explicitly evaluated against the deferred production-modularization constraint; reflection must not be used merely to simulate typed coverage.
